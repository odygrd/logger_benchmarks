Logger Benchmarks

Performance benchmarks for various C++ logging libraries.

All repo helper scripts live under `tools/`.

## Quick Start

Restore the pinned dependencies:

```bash
python3 tools/bootstrap_deps.py
```

Configure and build everything:

```bash
cmake -DCMAKE_BUILD_TYPE=Release -S . -B cmake-build-release
cmake --build cmake-build-release
```

Run every benchmark, five passes:

```bash
python3 tools/run_all.py
```

Generate markdown tables from the collected results:

```bash
python3 tools/generate_tables.py --stat median > tables.md
```

## Dependencies

Git-based third-party sources are pinned in `vendor_manifest.json` and managed by `tools/update_vendor.py`.

`third_party/boost` is generated by `tools/setup_boost_simple.py`. To refresh an existing Boost installation, run `python3 tools/setup_boost_simple.py` before configuring CMake.
`tools/bootstrap_deps.py` is the one-shot wrapper that restores both the git-based dependencies and Boost.Log.
If `third_party/boost` is missing during CMake configure, the build now bootstraps Boost.Log automatically so the Boost benchmarks are always added.

### Download The Pinned Versions

Use this when you want the exact versions already recorded in the manifest, without advancing anything upstream:

```bash
python3 tools/bootstrap_deps.py
```

If you only want to resync the git-based vendored repos and leave Boost alone:

```bash
python3 tools/update_vendor.py sync --all
```

### Update To The Latest Upstream Tips

Use this when you want to move the manifest and the vendored trees to the latest remote branch tips:

```bash
python3 tools/update_vendor.py sync --all -update
```

`-update` and `--update` are equivalent.

For each selected dependency, the updater:

1. fetches the remote into `.vendor-cache/`
2. resolves the latest commit from the configured update branch
3. uses `origin/master` by default, unless a dependency declares `"update_branch"` in `vendor_manifest.json`
4. falls back to the remote default branch if the selected branch does not exist
5. replaces the vendored directory with the raw upstream snapshot
6. writes the resolved commit back to `vendor_manifest.json`
7. stages the affected manifest and vendor paths so `git commit` can include them directly

Dependencies with `"skip_update": true` in `vendor_manifest.json` are left on their pinned refs during
`--update`. `fmt` currently stays pinned to the upstream `12.2.1` release.
`spdlog` currently tracks `origin/v1.x` during `--update`.

You can also update a single dependency:

```bash
python3 tools/update_vendor.py sync fmtlog -update
```

### Useful Vendor Commands

```bash
python3 tools/update_vendor.py list
python3 tools/update_vendor.py resolve --all
python3 tools/update_vendor.py capture-patch --all
python3 tools/update_vendor.py sync fmtlog
python3 tools/update_vendor.py sync fmtlog --ref v2.3.0
python3 tools/update_vendor.py sync fmtlog -update
```

Treat every `target_dir` listed in `vendor_manifest.json` as vendor-owned. Local fixes should live in
`vendor_patches/<name>/`, not as undocumented manual edits inside vendored source trees.
If you intentionally change a vendored tree and want to re-record that delta, run `capture-patch`.
The `--update` path does not reapply or refresh `vendor_patches`; it stages the raw upstream tree.

## Benchmarks

### Call Site Latency

`benchmarks/call_site_latency` times the log call on the calling thread. Every library is built once per payload
(`int_int_double`, `int_int_largestr`, `vector_largestr`) and scenario, as
`benchmark_<library>_call_site_latency_<payload>_<scenario>`:

| Scenario | Threads | What a sample is |
|----------|---------|------------------|
| `single` | 1 and 4 | One call, every 100 to 300 us |
| `burst` | 1 and 4 | The mean of 20 back-to-back calls per thread, every 2 to 2.2 ms |
| `cold` | 1 | One call after the caller has read a buffer four times the size of its L2 cache (at least 4 MiB), so the logger's data comes from L3 or memory |
| `disabled` | 1 | A debug statement while the level is info: the mean of 1,000 calls (`disabled_hot`) and one call after the cache sweep (`disabled_cold`) |

- All threads follow the same schedule, so with four threads the calls of a sample are made at the same time.
- Payloads are built before timing, and the first iterations are a warm-up that is not recorded.
- Results are printed in nanoseconds with one decimal, including the worst sample.
- The cold scenario prints how long a line read before the sweep takes to reload, to show that the sweep evicts
  the L2 cache.

Every scenario gives every library the same settings where it has them:

- The backend never sleeps: Quill `sleep_duration = 0`, BqLog `log.worker_interval_ms=0`, and loops that never
  sleep for fmtlog and MS BinLog, whose applications own the backend loop.
- Each library's default queue capacity, blocking when full (fmtlog `FMTLOG_BLOCK=1`).
- Timestamps read on the calling thread where the library offers it (XTR `XTR_LOGL_TSC`).

These are not every library's defaults: Quill's backend sleeps 500 us when idle, BqLog's worker up to 66 ms,
fmtlog's polling thread polls once a second and its queue drops messages when full, and XTR uses io_uring. The
Quill benchmarks page describes each library's defaults in its notes.

### Throughput

`benchmarks/backend_total_time` logs 4,000,000 messages and times until every message has been written to the
file. `BENCHMARK_<library>_backend_total_time` uses one producer thread and
`BENCHMARK_<library>_backend_total_time_4_threads` four, each logging a quarter of the messages. Both report when the
producers finished and when the last message was written.

- Each library keeps its default queue type and size, as in the latency benchmarks, blocking when a queue is full
  so no message is dropped.
- The clock stops once the data has been handed to the kernel: XTR uses a storage without `fsync`, and spdlog stops
  when its worker has flushed, before the thread pool shuts down.

The messages come from 256 distinct statements with one to five mixed arguments each (integers, doubles, strings
and chars), in a fixed pseudo-random order. An application has hundreds of statements, so the backend sees many
format strings, argument types and call sites rather than the same few. Every library writes the same messages with
the same pattern. The statements are generated by
`tools/gen_many_statements.py` into `benchmarks/backend_total_time/many_statements/`, one file per call style:
`{fmt}` format strings, C conversions for PlatformLab NanoLog, Reckless's conversions, and streams.

## Running Benchmarks

`tools/run_all.py` finds every benchmark binary in the build directory and runs them one at a time, writing
`bench_results_run<pass>_<n>.txt` files in the repo root. By default it makes five passes.

```bash
python3 tools/run_all.py
python3 tools/run_all.py --passes 3 --scenarios single throughput
```

- Each pass runs the binaries in a random order. The seed is printed and recorded in every results file; pass
  `--seed` to repeat an order.
- Dirty pages are written back between binaries, so one benchmark's log file is not written to disk during the
  next one.
- Every results file starts with the system configuration (kernel, CPU, kernel command line, governor, turbo, idle
  states) and ends with a delivery check: the lines of each text log against the lines the benchmark should have
  written. A `FAIL` is also printed while running. The log files are deleted afterwards unless `--keep-logs` is
  given.

The benchmarks use CPUs 0-5 for their caller and backend threads, so those CPUs must be available to the process.
The runner gives BqLog's worker an initial CPU 5 affinity because BqLog creates that worker before the benchmark
repins its caller threads. Do not run anything else on the machine at the same time.

## Generating Tables

`tools/generate_tables.py` scans the repo root for `bench_results_*.txt` and prints markdown tables for every
scenario, the disabled statement and throughput with one and four producers.

```bash
python3 tools/generate_tables.py --stat median > tables.md
```

`--stat` chooses how the passes of each library are combined:

- `mean` (the default): the mean of every value.
- `median`: the median of every value, recommended with five or more passes.
- `best` (or `--best-of-runs`): each library's best run, the lowest 90th percentile (then 95th, 99th and 99.9th)
  for latency and the highest msg/s for throughput.

The same rule applies to every library.

`--format rst` prints reStructuredText `list-table` blocks instead, as the
[Quill benchmarks page](https://quillcpp.readthedocs.io/en/latest/benchmarks.html) uses:

```bash
python3 tools/generate_tables.py --stat median --format rst > tables.rst
```

`--format json` prints every table's rows as data. The Quill documentation builds its benchmark pages, with
the Linux and Windows results side by side, from one such file per platform:

```bash
python3 tools/generate_tables.py --stat best --format json > results_linux.json
```

## Windows (MSVC)

The benchmarks also build and run on Windows with MSVC. Linux builds are unaffected: every
Windows change is behind a `WIN32`/`MSVC` CMake condition, an `#if defined(_WIN32)` block or an
`os.name == "nt"` check.

### Build

Use an x64 Visual Studio developer environment (`x64 Native Tools Command Prompt`, or
`vcvars64.bat`) with the Ninja generator that ships with Visual Studio.

Boost.Log is built by `tools/setup_boost_simple.py` using the default CMake generator. Set
`CMAKE_GENERATOR=Ninja` so it is built and installed as a single-configuration Release build:

```bat
set CMAKE_GENERATOR=Ninja
python tools\setup_boost_simple.py
```

Configure and build:

```bat
cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=cl -DCMAKE_CXX_COMPILER=cl -S . -B cmake-build-release
cmake --build cmake-build-release
```

With MSVC the compile flags are `/DWIN32 /D_WINDOWS /EHsc /GR /utf-8 /arch:AVX2` plus the CMake
Release defaults `/O2 /Ob2 /DNDEBUG`. `/arch:AVX2` is the MSVC equivalent of the Linux
`-march=x86-64-v3` build and `/utf-8` is required by the bundled `fmt` in spdlog.

### Libraries Excluded On Windows

| Library             | Reason                                                                                                  |
|---------------------|---------------------------------------------------------------------------------------------------------|
| XTR                 | Linux only (POSIX file descriptors, `mmap`, io_uring)                                                    |
| PlatformLab NanoLog | Linux only (POSIX AIO, `unistd.h`)                                                                      |
| Iyengar NanoLog     | Does not compile with MSVC (`flag{ ATOMIC_FLAG_INIT }` in `NanoLog.cpp`)                                |
| Reckless            | Does not compile with MSVC and the current Windows SDK (its Win32 API redeclarations conflict with the SDK) |

Their targets are not added on Windows and `tools/run_all.py` skips their benchmarks.

### CPU Affinity

There is no `taskset` on Windows. On Windows `tools/run_all.py` starts each benchmark directly with
`HIGH_PRIORITY_CLASS`, and the benchmarks pin their threads in-process with
`SetThreadAffinityMask`.

The benchmark CPU numbers (0 main thread, 1-4 caller threads, 5 backend thread) are mapped by
`bench_cpu()` in `benchmarks/bench_platform.h` to the first logical processor of distinct physical
cores, preferring the highest performance efficiency class (P-cores on hybrid CPUs), so the
benchmark threads never share an SMT sibling. On Linux `bench_cpu()` is the identity mapping.

Windows threads start with the process affinity rather than the affinity of the thread that
created them. For loggers that do not expose their worker thread (BqLog, g3log), the benchmarks
call `pin_other_threads_on_windows(5)` after the logger is initialised, which pins every other
thread of the process to the backend CPU. It is a no-op on Linux.

### Run

```bat
python tools\run_all.py
python tools\generate_tables.py
```
